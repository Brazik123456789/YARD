# Yandex Business Discovery

Дата исследования: 31 октября 2026. Статусы доказательств: **наблюдалось** — увидено в UI или Network; **документация** — сведения Яндекса; **не проверено** — нельзя считать подтверждённым. Пользователь выполнил согласованные действия с ответами и жалобой; запросы описаны в разделах 27, 29–31. ## 1. Executive Summary

Внутренние HTTP-запросы кабинета для организаций, филиалов, отзывов, создания, изменения и удаления ответа и отправки жалобы наблюдались в Network. По операциям записи наблюдались HTTP 200 и текст `OK`; это не подтверждает прохождение модерации или решение по жалобе. Запросы выполнены кабинетом, а не будущим коннектором Yard. Согласован PoC: отдельный Playwright BrowserContext на технический аккаунт, ручной вход, операции через связанный APIRequestContext. Совместимость, восстановление сессии и масштаб требуют проверки при разработке. API недокументирован; главные риски — изменения контракта, сессии, лимиты и условия использования.

## 2. Account / Access Model

В кабинете под одной учётной записью видна сеть Главпрокат и два филиала. В данных кабинета роль сети и объекта списка обозначена `delegate` (наблюдалось в JSON/state); точное название роли в UI и все её полномочия не проверены. Доступ к двум точкам одной сети подтверждён; несколько независимых сетей и ограничения на их количество не проверены. Открытие формы жалобы отметило отзыв прочитанным — просмотр может менять служебное состояние.

## 10. Authentication / Session

Наблюдалась авторизованная сессия браузера Яндекс ID; на запросе GET браузер показывал `Accept`, `Referer`, `User-Agent`, `X-Requested-With`, client hints. Заголовки со значениями и секреты не сохранялись. Механизм refresh и срок жизни неизвестны. Не утверждать, что перенос cookie достаточен: проверить на отдельном авторизованном стенде, не логировать секреты, ограничить доступ и шифровать секреты.

## 11. XHR / HTTP API Findings

### Список отзывов — наблюдался Fetch

Список организаций и филиалов: JSON GET, раздел 20. Запросы создания/изменения/удаления ответа — разделы 27, 29 и 30; жалобы — раздел 31. Отдельный endpoint одиночного отзыва не наблюдался. UI-маршруты и внутренние endpoint не являются подтверждённым официальным API.

## 12. Pagination / Polling / Events

UI использует `page`, response `pager.limit=20`, `offset`, `total`; подтверждена вторая страница. `ranking=by_time` и `by_rating_asc` наблюдались. Cursor/фильтр после времени, webhook, SSE, WebSocket и push для отзывов не обнаружены; отсутствие не доказано. Предлагаемый эксперимент: периодически опрашивать первые страницы по времени с перекрытием, upsert по `(provider, location_id, review_id)`, сравнивать изменения ответа и полей; отдельно периодически проходить более глубокую историю для правок и удалений. Проверить пограничные случаи одинаковых дат, поздней модерации, удаления, порядка и времени обработки. Интервал N установить по измерениям и согласованной допустимой задержке, не выдавать его за лимит Яндекса.

## 13. Multiple Organizations / Scaling

Одна браузерная сессия последовательно открыла две точки и вызвала один и тот же маршрут с различными location ID, получив 200. Это подтверждает адресацию по ID внутри браузера, но не доказывает отсутствие влияния UI-состояния: перед запросами соответствующие страницы открывались. Независимый HTTP, перемежение запросов без переходов, параллелизм, конкуренция, лимиты и rate limiting не проверены. Начинать PoC последовательно с ограниченной частотой, метриками, backoff и изоляцией клиентов; не обещать масштаб до нагрузочных проверок.

## 15. Browser Automation Requirements

Точно необходимо UI для проведённого исследования формы; техническая необходимость Playwright для любого действия не установлена. Список отзывов уже загружается браузером по HTTP, но внешний HTTP-клиент ещё не проверен. Login/session recovery, ответы и жалобы могут потребовать браузер либо другую интеграцию — пока гипотеза. Не подменять доказательство HTTP 200 внутри браузера доказательством работы без браузера.

## 16. Risks

Недокументированный API и изменения схемы; отзыв доступа и ограничения роли; CSRF и истечение сессии; CAPTCHA/антибот и блокировки; неизвестные лимиты; разные счётчики и задержка синхронизации; потеря или удаление ответов после изменения отзыва; риск повторной отправки при таймауте; жалоба однократная; доступ технической учётной записи к нескольким клиентам и изоляция данных; проверка условий использования перед запуском. Чтение UI может менять непрочитанность.

## 17. Recommended YandexConnector Architecture

Согласованное направление: отдельный Playwright BrowserContext и связанный APIRequestContext на технический аккаунт; ручной вход, далее HTTP-запросы. Отсутствие необходимости навигации по точкам предстоит проверить. Адаптер с `discoverLocations`, `listReviews`, `writeReply`, `submitComplaint` и capability flags; очередь, upsert, журнал без секретов и алерты. Запросы записи кабинета наблюдались; воспроизведение этим клиентом не проверено. Для жалобы сохранять неизвестный исход и не трактовать факт подачи как решение. См. раздел 21.

## 20. Дополнение: организации и филиалы (31 октября 2026)

**Организации.** При очистке поля поиска наблюдался `GET https://yandex.ru/sprav/api/companies?filter=` → HTTP 200 `application/json`, без body. Ответ содержит `listCompanies`, `filter`, `page`, `total`, `limit`, `advIconSkeletonLoading`. Без фильтра: `page=1`, `total=1`, `limit=10`, единственный объект сети: `type=chain`, `id=permanent_id=29777163084`, `tycoon_id=28283710`, `object_role=delegate`. Страница `GET /sprav/companies/?no_redirect=1` также включает список в `window.__PRELOAD_DATA.initialState.companiesList` с `listCompanies`, `page`, `total`, `limit`, `defaultPagerLimit=10`, `limitScale=[10,20,50]`. Это данные текущего экрана, не доказательство, что все страницы возвращаются за один запрос. Свыше одной страницы не проверено.

`GET /sprav/api/companies?filter=<URL-encoded название>` → HTTP 200 JSON: поиск «Главпрокат» вернул 3 карточки `type=ordinal` вместо одной свёрнутой сети. Помимо двух действующих найден объект 2689917020 с отображаемым статусом «Переехала». Все три имели `noAccess=false` и ссылку `chain.permanent_id=29777163084`; права на отдельные операции не проверены. Не смешивать результаты поиска с неотфильтрованной иерархией сети и не считать количество открытых филиалов полным числом всех карточек.

**Филиалы.** При выборе в UI фильтра «Все филиалы» наблюдался `GET https://yandex.ru/sprav/api/chain/28283710/branches?status=all&chainPermalink=29777163084&geoId=225&page=1` → HTTP 200 JSON, без body. Ключи ответа: `companyList`, `companyIds`, `companiesPermalinks`; `companyList` содержит `pager`, `chain`, `companies`. Начальное состояние при фильтре `status=opened` содержит `pager={limit:20,offset:0,total:2}`; при `status=all` также вернулись две записи и `total=2`; переехавшая карточка из результатов поиска в этом ответе отсутствовала. Причина и актуальная принадлежность этой карточки требуют проверки. До выбора фильтра те же структурированные данные находятся в `window.__PRELOAD_DATA.initialState.chain.companyList`.

Для действующих филиалов обнаружены два разных ID: Уфа внутренний `id=21845831`, `permanent_id=116945153338`; Оренбург внутренний `id=54277280`, `permanent_id=57933644573`. В URL отзывов используется permanent_id. `companyIds` содержал внутренние id, `companiesPermalinks` — permanent_id; их нельзя подменять. В `initialState.chain.chainRoles` роль текущего доступа — `delegate`.

**Сессия.** В браузере существуют cookies домена Яндекса, в том числе HttpOnly `Session_id`, `sessionid2` и другие. Наличие не доказывает, какие из них необходимы для API, и не устанавливает срок жизни авторизации. Значения не сохранялись. Изолированное воспроизведение отдельным HTTP-клиентом, сравнение обязательных заголовков, межфилиальные запросы без UI-переходов, проверка влияния polling на прочитанность и долговечности сессии в этом проходе не выполнены. Поэтому первый этап завершён частично; работа через HTTP вне браузера остаётся неподтверждённой.


## 21. Согласованный вариант интеграции и план PoC

### Статус решений

**Решение пользователя для PoC:** гибридный коннектор: браузер Playwright используется для ручного входа и управления сессией каждого технического Яндекс ID; основные операции должны выполняться HTTP-клиентом `browserContext.request` (`APIRequestContext`), связанным с тем же контекстом. Нет необходимости копировать cookies в отдельный Java HTTP-клиент или обновлять UI каждой точки для каждого запроса, если PoC подтвердит работу. Возможность обращения к endpoint без UI-переключения пока не проверена. Это направление для исследования и последующей реализации, а не доказательство промышленной работоспособности, допустимости или масштабируемости.

[Документация Playwright API testing](https://playwright.dev/docs/api-testing): связанный `APIRequestContext` использует cookie storage BrowserContext и обновляет cookies браузера из `Set-Cookie` ответа API. Это относится к cookies; автоматическое получение произвольных CSRF, access или иных токенов не гарантировано. Проверить применимость к реальным запросам Яндекса. Само существование access/refresh tokens и их срок жизни в данной интеграции не установлены. `business_answer_csrf_token` наблюдался по отзыву; реальное назначение, обязательность и срок действия не проверены.

### Несколько технических аккаунтов

- Один отдельный изолированный BrowserContext и связанный HTTP-клиент на технический аккаунт. Обычные вкладки внутри одного контекста делят cookies и не обеспечивают изоляцию учётных записей. Фактическая визуализация входа — окно или вкладка — определяется реализацией удалённого браузера; не гарантировать, что отдельные контексты будут видны как обычные вкладки одного окна.
- Сессия аккаунта используется для организаций и точек, доступ к которым реально выдан этому аккаунту. Не отождествлять технический аккаунт, клиента Yard, сеть и филиал. Предусмотреть назначение точек аккаунтам, проверку прав и изоляцию клиентов. Объём доступа и лимиты одной учётной записи не проверены.
- Потеря сессии одного аккаунта при исправных остальных не должна останавливать их обработку. Для одной учётной записи ограничивать конкуренцию, собирать метрики и предусмотреть backoff; допустимый параллелизм и лимиты неизвестны.

### Служебная страница управления

Согласованный пользовательский сценарий для администратора Yard:

1. Открыть защищённую служебную страницу интеграции, добавить технический Яндекс-аккаунт и нажать «Открыть браузер».
2. В открытом контексте вручную войти в Яндекс; пароль и подтверждения вводятся непосредственно в Яндексе, CAPTCHA или второй фактор проходит пользователь.
3. Вернуться на служебную страницу и нажать «Проверить подключение». Коннектор проверяет сессию, получает доступные организации и филиалы и показывает результат и ограничения.
4. Администратор нажимает «Запустить работу» отдельно от входа; обработка выполняется только для разрешённых и выбранных для обслуживания точек.
5. Показывать состояние по аккаунту: подключён, проверяется, требуется повторный вход, ошибка; предусмотреть остановку и повторное подключение конкретного аккаунта. Ожидаемый удалённый доступ к серверному браузеру и его защита требуют отдельного проектирования.

Для первой версии не обязательно хранить пароли Яндекс ID: ручной вход и безопасное сохранение состояния сессии предпочтительны. Состояние содержит чувствительные данные; шифрование при хранении, ограниченный доступ, отсутствие секретов в логах, git и диагностических файлах. Если необходимо переживать рестарт — проверить безопасное восстановление состояния; оно может быть отклонено Яндексом. См. [Playwright Authentication](https://playwright.dev/docs/auth).

### Поддержание сессии и фоновые запросы

Пользователь предложил периодически обновлять браузерную страницу, чтобы поддерживать сессию и актуальность данных. Согласовано оставить это **настраиваемым экспериментом**. Нет доказательства, что обновление страницы продлевает сессию: фиксированный срок, серверная инвалидизация, повторный вход или CAPTCHA могут потребоваться независимо от активности. Нет оснований утверждать, что refresh раз в 1–2 или 2,5–5 минут необходим или безопасен. Не делать случайный интервал средством обхода защит.

Рабочие HTTP-запросы уже являются обращениями к Яндексу. Состояние проверять на успешных рабочих запросах и при необходимости отдельной проверкой; различать истечение авторизации, отказ в правах, CAPTCHA, rate limit и временную ошибку. Проверять тип и структуру ответа, а не считать любой HTTP 200 успешной авторизацией. При необходимости повторного входа останавливать задания соответствующего аккаунта и уведомлять администратора; не решать CAPTCHA автоматически.

Сравнить два режима в PoC: без фонового обновления страницы и с настраиваемым интервалом обновления. Наблюдать частоту, изменения cookies и сетевые refresh-запросы, состояние сессии, требование повторного входа и побочные эффекты. Не записывать содержимое cookies или токенов. Выводы о сроке жизни требуют длительного наблюдения; отсутствие ошибки во время короткого теста не доказывает, что сессия не истечёт.

### Опрос отзывов

10–30 минут на точку — предложенный ориентир для PoC, а не установленный лимит Яндекса и не обещание SLA. Разнести запросы во времени, учитывать общее число точек, число страниц, аккаунт и повторы. Например, 1000 точек / 10 минут = в среднем 100 запросов в минуту только на первую страницу; 1000 организаций может означать существенно больше точек. Проверить пропускную способность и условия Яндекса до промышленного масштаба.

Для обнаружения новых отзывов предварительно читать последние страницы в сортировке `by_time` с перекрытием и дедупликацией по `(provider, location_permanent_id, review_id)`; дополнительно сверять более старые данные для поздних публикаций, изменений и исчезновения ответов/отзывов. Стабильность ID, точность времён, поведение изменённых и удалённых отзывов, порядок результатов и влияние GET на непрочитанность не подтверждены. UI-открытие формы жалобы ранее отметило один отзыв прочитанным. Период и глубину сверки выбрать по результатам проверки и требованиям продукта.

### Конкретный план проверки

1. Создать изолированный контекст для одного технического аккаунта, пользователь входит вручную.
2. 8. Проверить производительность и ограничения постепенно и в согласованных пределах; нет доказательств, что один аккаунт способен обслуживать тысячи организаций. Разобраться с официальным/партнёрским API и условиями автоматизированного использования.
